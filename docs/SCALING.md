# 大規模生成・保存の検証（2026-10-14）

生成器の拡充とは分け、math.expression、seed 42、動的100%を共通条件として、最適化前後を問題数ごとに新しいPythonプロセスで測定した。Cloud Linux / Python 3.12.14、各条件1回の観測値。モデルの推論速度やWindows性能の測定ではない。

| 問題数 | 最大RSS: 前 → 後（MB、10進） | 生成時間: 前 → 後（秒） |
|---:|---:|---:|
| 100 | 25.68 → 25.55 | 0.0107 → 0.0116 |
| 1,000 | 31.97 → 28.30 | 0.1113 → 0.0952 |
| 8,000 | 80.61 → 52.03 | 0.8384 → 0.7994 |

8,000問では最大RSS約35%削減。時間の小差は単発測定で、統計的な高速化の主張はしない。生成問題全体を辞書化してからJSON化する処理を、1問ずつ同じcanonical形式でハッシュへ渡す処理へ変更した。固定銀行は生成器別に候補を分け、入力ハッシュを再利用する。シャッフル・同距離候補の順序・カテゴリ配分は維持した。

この最適化だけでは旧ハッシュが完全一致することをgoldenテストで検証。別変更の採点版1.1.0や生成器版の更新は、新規セットのハッシュを意図的に変える。過去のセット本体・採点版・ハッシュを上書きしない。

## 保存・復元・出力

8,000問に人工の正解/誤答結果を交互に投入し、途中でStoreを開き直して復元、timeout再試行、同一結果の重複投入、50件ずつ全160ページを読み出し、分割gzipを検証した。

- 確定結果8,000件、試行8,002件、正答4,000／分母8,000、正答率0.5。
- 全問・結果・試行を含む24,003レコード、22分割gzipのマニフェスト検証成功。
- 保存0.094秒、簡易集計0.305秒、全ログページ取得0.284秒、分割出力0.785秒。
- ライフサイクル全体のプロセス累積最大RSS約102.3MiB。集計や復元を含むため、生成単独の測定とは分けて扱う。
- CIは60問で50件ページ境界をまたぎ、DBトランザクションの途中失敗、巻き戻し、復元の冪等性、遅れて届く旧試行の結果拒否を検証する。

測定値は[開発用記録](../dev_reports/2026-10-14-scaling.json)に保存。実モデルを呼び出さず、実スケジューラーの長時間運転・数日耐久・GPU負荷を測ったものではない。

## 再実行

リポジトリ直下で実行する。既存のuv環境だけを使用し、GPUや追加モデルは不要。

```text
uv run --no-sync python scripts/profile_sets.py --counts 100 1000 8000
uv run --no-sync python scripts/profile_lifecycle.py --count 8000
```

後者は新しい一時ディレクトリへ結果DBとアーカイブを作る。保存場所を管理したい場合は `--output <まだ存在しないフォルダ>` を指定する。実行後に表示されたフォルダを削除すれば測定データを片付けられる。

## 残る制約

- freezeは全Problemオブジェクトを保持する。ハッシュ時の追加コピーは減ったが、完全な一定メモリ生成ではない。
- 固定銀行は各生成器20問であり、8,000問の固定50%指定を満たす銀行ではない。不足はエラーにする。
- 全生成器を選ぶ大規模動的生成も、有限ドメインの重複除外で不足する場合がある。旧24種の8,000問指定ではlanguage.scopeの候補枯渇を確認した。問題数を埋めるために重複を許容したり他分野へ置換したりしない。
- 長文問題の本文量、結果の回答長、同時に表示する履歴数でメモリや待ち時間は変わる。今回の数値を全種類へ外挿しない。
