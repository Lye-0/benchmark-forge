# feat: Windowsネイティブ対応と隔離実行環境の分離

## 目的

現在の `benchmark-forge` は、WSL2 Ubuntu / Linuxを主な実行環境として想定しています。

これを変更し、**Windows 11を主要な実行環境としながら、既存のLinux / WSL2対応も維持するクロスプラットフォーム構成**にしてください。

単なるWindows用起動スクリプトの追加ではなく、アプリケーション全体についてWindowsとの互換性を確認し、必要な修正を実施してください。

既存の機能、セキュリティ、データ形式、評価結果の再現性を損なわないことを重視します。

---

## 1. 目標アーキテクチャ

### 通常実行：Windowsネイティブ

次のコンポーネントは、WSL2を経由せずWindows上で直接実行できるようにしてください。

- Web UI（React / Vite）
- Pythonバックエンド
- 問題生成器
- 問題の検証・採点
- SQLite等のデータ管理
- ベンチマーク実行管理
- OllamaによるローカルLLM推論
- Transformers / PyTorchによるローカル推論
- NVIDIA CUDAによるGPU推論
- Codex CLI / Codex App Server連携
- 結果分析、履歴表示、エクスポート

ブラウザから `http://localhost:8000` のようなアドレスで利用できる構成を維持してください。

通常の数学、論理推論、文章理解、データ処理などのベンチマークでは、DockerやWSL2を起動する必要がないようにしてください。

### 隔離実行：必要な場合だけ仮想化環境を使用

LLMが生成したコードのコンパイル・実行や、信頼できないプログラムの実行が必要な場合のみ、安全な隔離実行環境を使用してください。

第一候補はWindows上のDocker DesktopによるLinuxコンテナです。

Docker Desktopの内部でWSL2などの仮想化基盤を利用することは許容します。

ただし、ユーザーが毎回Ubuntuを手動起動したり、WSL2上でアプリ本体を操作したりする必要はない構成にしてください。

また、Docker Desktopは通常利用の必須依存関係にしないでください。

---

## 2. Windows対応の実装

既存コードを調査し、Linux固有の実装やWindowsで正常動作しない可能性のある部分を特定してください。

特に以下を確認してください。

- ファイルパスおよびパス区切り文字
- subprocess、プロセス管理、停止処理
- POSIX固有のAPIやシグナル
- Bashスクリプトへの依存
- 権限・ファイル操作
- 環境変数
- 一時ディレクトリ
- SQLiteのロックと同時アクセス
- ローカルサービスへの接続
- 依存パッケージのOS互換性
- バックエンドの起動・終了処理

可能な限りプラットフォーム共通の実装を使用し、OS固有処理が必要な部分は明確に分離してください。

Linux対応を削除したり、Windows専用の実装へ置き換えたりしないでください。

### PowerShellによるセットアップ

Windows向けに、少なくとも以下に相当するスクリプトを用意してください。

- `scripts/setup.ps1`：初回セットアップ
- `scripts/start.ps1`：通常起動
- 必要に応じて停止・診断用スクリプト

既存の `setup.sh` や `start.sh` は維持してください。

Python依存関係には既存のuv管理を利用し、Node.js側の依存管理も既存プロジェクトの方式を尊重してください。

実行ポリシーや証明書検証、セキュリティ機能を無条件に無効化する方法は使用しないでください。

Windows向けに不要なLinux専用依存関係をインストールしないようにしてください。

## 3. Windows上のLLMバックエンド

### Ollama

Windows版Ollamaに接続できるようにしてください。

- localhost上のOllamaサービスへ接続
- モデル一覧の取得
- モデル登録
- 接続確認
- 実際の推論
- 推論設定の適用
- エラー・タイムアウト処理

Linux側でOllamaを起動することを必須にしないでください。

### Transformers / PyTorch

Windows版PyTorchおよびCUDAによるGPU推論をサポートしてください。

CPUでも基本動作できるようにしてください。

GPUの有無、CUDAの利用可否、メモリ情報を適切に取得してください。

CUDAが利用できない場合にもアプリ全体が起動不能にならないようにしてください。

### Codex CLI / Codex App Server

既存の接続設計を維持し、Windows上で動作できるようにしてください。

公式の認証・連携方式のみを使用してください。

認証ファイルの不正な流用や、セキュリティ制限の回避は行わないでください。

実モデルによる検証が実施できない場合も、実装を可能な限り完成させ、Mockによる接続・プロトコル・エラー処理のテストを実施してください。

未検証の機能を検証済みと記載しないでください。

## 4. 隔離実行エンジン

ここは特に慎重に実装してください。

既存のLinux向けコード実行サンドボックスを調査し、Windowsから利用できる構造へ変更してください。

WindowsのPythonバックエンドから隔離されたLinuxコンテナにコードを渡し、実行結果を取得する仕組みを想定しています。

以下を必須要件とします。

- ホストの個人ファイルへアクセスできない
- 認証情報・秘密鍵をコンテナへ渡さない
- Dockerソケットをコンテナへ渡さない
- ネットワークは原則無効
- CPU、メモリ、PID数、実行時間を制限
- 不要なLinux capabilitiesを削除
- 特権コンテナを使用しない
- 読み取り専用ファイルシステムを原則とする
- 必要な書き込み領域のみ限定して提供
- コンテナの実行・終了・後片付けを管理
- 可能な範囲でseccomp等の制限を利用
- 危険なコードがホスト側で直接実行されない

Dockerコンテナだけで完全な隔離を保証できるわけではないことを前提に、安全性を検証してください。

**安全な隔離を確認できない場合は、コード実行型ベンチマークを無効化してください。**

隔離機能が使用できないことを理由に、Windows上で生成コードを直接実行するフォールバックは絶対に実装しないでください。

隔離機能が利用できない場合でも、それを必要としないベンチマークは正常に実行できるようにしてください。

### 隔離環境の状態確認

アプリから隔離環境の利用可否を診断できるようにしてください。

例えば、Web UIで以下を確認できる構成が望ましいです。

- Docker利用可能
- Docker未インストール
- Docker停止中
- 隔離環境の検証失敗
- コード実行ベンチマーク利用可能 / 利用不可

WindowsではDocker Desktopの利用を第一候補とし、既存のLinux環境でも動作する構成にしてください。

既存の黒基調のデザインを維持してください。

必要な部分に限り、利用者が分かりやすい情報を追加してください。

通常のベンチマーク、実行中の進捗表示、暫定スコア、結果概要、詳細ラン、履歴、比較などの既存機能は維持してください。

## 6. テストと品質保証

Windows対応を実装した後、次の内容を確認してください。

### クロスプラットフォームテスト

- WindowsでPythonバックエンドが起動する
- WindowsでWeb UIが起動する
- 問題生成と採点が正常に動作する
- データの保存・読み込みが成功する
- 中断・再開が正常に動作する
- モデルアダプターが適切に初期化される
- Linuxで既存機能が引き続き動作する

可能ならGitHub ActionsでWindowsとLinuxのテストを実施してください。

### 隔離テスト

- Dockerが存在しない場合の動作
- Dockerが停止している場合の動作
- コンテナのタイムアウト
- CPU・メモリ制限
- ファイルシステムの隔離
- ネットワークアクセス制限
- 異常終了後のクリーンアップ
- 安全性検証に失敗した場合の機能停止

セキュリティ機能が動いていることを、単なる設定値の存在だけで判断しないでください。

### 開発中のLLM評価

以前の方針を維持してください。

開発中に実際のLLMへ問題を解かせるテストでは、Codex Cloud上で利用可能なサブエージェントを使用してください。

サブエージェントに問題文だけを渡し、正解や採点情報を参照させずに解答させてください。

結果は開発用の品質確認にのみ使用し、正式なモデルベンチマークの結果には混ぜないでください。

通常の単体テスト・統合テスト・セキュリティテストは別途実施してください。

## 8. 開発の進め方

まず既存リポジトリを十分に調査し、必要な変更を整理してから実装してください。

既存コードを無計画に全面的に書き換えないでください。

次の順番を推奨します。

1. 現在の構成とOS依存箇所を調査
2. クロスプラットフォームの共通部分を整備
3. Windows起動・セットアップを実装
4. Windows側のモデル接続を整備
5. 隔離エンジンのWindows対応
6. Web UIの接続状態・エラー表示を整備
7. Windows / Linuxの自動テスト
8. セキュリティレビュー・修正
9. ドキュメントの更新
10. 最終レビュー

各段階で既存機能が壊れていないことを確認してください。

開発中に発見した重大な不具合や安全性の問題は、対象範囲内で適切に修正してください。

コミットする場合は日本語のConventional Commits形式にしてください。

例：

`feat: Windowsネイティブでの起動に対応`

`fix: 隔離実行環境の権限制限を修正`

`docs: Windows向けセットアップ手順を追加`

## 9. 完成条件

以下を満たした状態を目標とします。

- Windows上でPowerShellからアプリを起動できる
- WSL2が起動していなくても通常のベンチマークを実行できる
- Windows上のOllamaやPyTorchを使用できる
- 問題生成・採点・結果保存・分析がWindowsで動作する
- コード実行型ベンチマークだけ隔離環境を使用する
- 隔離が利用できない場合、安全に機能を無効化する
- WindowsとLinuxの双方で自動テストを実施できる
- 既存機能を維持する
- Windows向けの手順が整備されている

**最終的には、Windowsユーザーが普段WSL2の存在を意識せずに利用できることを目指してください。**

なお、Codex Cloudからは実際のWindows PCやGPU、Docker Desktopの状態を直接検証できない場合があります。

その場合は、実際に検証した項目、Mockによる検証項目、Windows実機での確認が必要な項目を明確に区別して報告してください。

設計だけで終了せず、可能な範囲で実装・自動テスト・修正・ドキュメント整備まで進めてください。
