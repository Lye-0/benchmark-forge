## 0. Codexへの最重要指示

あなたはこのリポジトリの実装担当である。**設計案だけ、雛形だけ、画面モックだけを提出して終了しないこと。** 本書を基に、動作するアプリケーション、テスト、ドキュメントを段階的に実装し、各フェーズの受け入れ条件を確認すること。

1. 最初にリポジトリ内の既存コードと指示ファイルを確認する。既存実装があれば尊重し、必要以上に作り直さない。
2. 作業計画を立て、実装・検証・修正を進める。フェーズごとに動く縦方向の一式（UI→API→生成→評価→保存）を完成させる。
3. 独立性が高い実装・調査・レビューは、利用可能ならサブエージェントに委譲してよい。同一ファイルへの無秩序な並列変更は避ける。
4. **問題生成にLLMを呼び出してはいけない。** Codex自体を開発・コードレビュー・開発時の問題解答試験に使うことは許可される。実行アプリの問題生成処理はアルゴリズム、規則、テンプレート、信頼できる参照データ、シミュレーターを使う。
5. **クラウドAPIの有料契約・APIキー・Claude契約は前提にしない。** Codex CLI / Codex App Serverは丁寧に実装するが、実アカウント接続が不可の場合は未検証と記録する。利用できないものを「実測済み」「対応済み」と表示してはいけない。
6. 開発中にAIが実際に問題を解く試験は、**Codex Cloudのサブエージェントが解く開発用試験**として扱う。正式ベンチマーク実行およびモデルランキングに混ぜない。通常の単体・統合・セキュリティテストは必ず別途実施する。
7. セキュリティを最優先する。生成コードの実行、ツール操作、エージェント実行は適切な隔離なしに行わない。隔離を確認できない環境では、当該機能を**無効化して明示**する。
8. 公開リポジトリ前提で、トークン、APIキー、アカウント情報、個人データ、認証キャッシュ、モデル重み、巨大な結果ファイルをコミットしない。
9. 仕様上の曖昧さは本書の原則から合理的に補う。重大な課金・セキュリティ・公開範囲・互換性の選択だけユーザーに確認する。通常の技術選定は自律的に進め、根拠を `docs/decisions/` に残す。
10. 各フェーズでテスト結果と未実装・未検証事項を正直に報告する。成功を装わない。変更はレビューしやすい単位に分ける。ユーザーの許可なく外部サービスへデプロイしない。
11. Gitコミットを作成するときは**日本語のConventional Commits**を用いる（例：`feat: 問題生成と採点の基盤を追加`）。GitHubリポジトリの選定・新規作成は行わない。

## 1. プロダクトの目的

### 1.1 コンセプト

**幅広い能力・分野・難易度の評価問題を、AIに依存せず継続的に自動生成し、ローカルLLMや利用可能なクラウドLLMを公正に比較する研究用ベンチマーク。**

- 多種多様な問題生成器を蓄積できる拡張可能な研究設備にする。
- 小型LLMから大型LLMまで、共通の問題群で比較可能にする。
- **正答率だけでなく、速度、レイテンシ、メモリ、実行条件、失敗傾向**まで測定する。
- 問題を固定した再現性の高い評価と、指定シードで新しい問題を作る評価を**決めた比率で統合**する。
- 「どの難易度辺りから解けなくなるか」を、各分野と全体で可視化する。
- 研究のために自分のPCで使うことが中心。Web公開サービスにすることは**今回の対象外**。

### 1.2 基本的な利用形態

- **localhostで動くダークテーマのWebアプリ**。クラウドホスティングはしない。
- バックエンド、問題生成、採点、履歴保存、ローカル推論はユーザーのPCで完結する。
- ローカルLLMなら、モデルとパッケージの用意後はオフライン利用可能。
- GPTなどのクラウドモデルを選択した場合にだけ外部接続が発生する。
- **CLIでも主要な機能を利用可能**とする。GUIはエンジンを呼び出すフロントエンドであり、評価ロジックを埋め込まない。
- 実装・検証の主作業はCodex Cloudで行い、成果物はユーザー指定のPublic GitHubリポジトリへ保存する。

### 1.3 非目標

- モデルの学習・ファインチューニングそのもの。
- 問題生成のたびにChatGPTやClaudeのAPIを呼び出すこと。
- 大量の見栄えだけの問題や検証不能な知識クイズを水増しすること。
- 誤解を招く単一の「知能・速度・VRAM混合点」を算出すること。
- API有料契約の取得、サービス購入、外部公開、ユーザーの既存プロジェクトへの侵襲的変更。

## 2. 既定の技術構成と裁量

以下を標準案とする。実装可能性・保守性に明確な理由がある場合は代替可。ただし理由をADRに記録する。

| 層 | 初期方針 |
|---|---|
| OS | Windows上のWSL2 Ubuntuを主対象。Codex Cloudでは通常のLinux上で開発・テスト |
| バックエンド | Python 3.12+、FastAPI、型ヒント、Pydanticなど |
| Python環境 | `uv` + `pyproject.toml` + ロックファイル。GPU依存をオプション化 |
| UI | React + TypeScript + Vite、アクセシブルなコンポーネント構成 |
| スタイル | ダークテーマ標準。Tailwind CSSなどの採用は実装側で判断 |
| 永続化 | SQLite（マイグレーションあり）、問題/評価データのJSONLエクスポート |
| 評価 | 生成エンジン、問題定義、モデルアダプター、採点器、実行スケジューラーを分離 |
| ローカルモデル | Transformers、Ollamaを初期優先。vLLM、llama.cpp/GGUFを追加可能な設計 |
| GPT系 | 公式のCodex CLI / Codex App Serverを主要なクラウド接続候補とする |
| 有料API | OpenAI互換API等はオプション。外部実APIを使わないMockテストに限定可 |
| 検証 | pytest、TypeScriptの型チェック・UIテスト、E2E、隔離のテスト |
| CI | GPU・秘密情報不要で動作するチェックをGitHub Actionsに設ける |

バックエンドとWebを別プロセスで起動する構成でよい。開発時のURL例は `127.0.0.1:5173`（UI）およびローカルAPI。**実際に占有されていないポートへ設定変更可能**にする。WSL→Windowsブラウザからアクセスできるようにする。

### アーキテクチャ（論理）

```text
Browser UI (localhost) ───── CLI
          │                     │
          └──── Application API ┘
                       │
              Benchmark Orchestrator
              ├── Category/Generator Registry
              ├── Deterministic Problem Generators
              ├── Validators / Graders
              ├── Fixed & Dynamic Set Builder
              ├── Run Scheduler / Resume / Progress
              ├── Model Adapters
              │    ├── Transformers / Ollama
              │    ├── Other local engines (optional)
              │    ├── Codex CLI / App Server
              │    └── Optional API adapters
              ├── Sandboxed Code/Tool Evaluator
              ├── Metrics Collector
              └── SQLite + Artifacts + Reports
```

Web表示に依存しないPython APIを作り、同じサービス層をCLI・UI・開発用検証で利用する。

## 3. 問題生成の原則

### 3.1 AIを使わない

本番の生成器は、乱数・アルゴリズム・数式・制約ソルバー・テンプレート・検証済み資料・模擬世界を使う。LLM API/CLI/サブエージェントによる問題文のその場生成はしない。

- 数学：SymPyや厳密計算。数値の許容誤差なども定義。
- 論理：Z3や全探索等。必要なら正解の一意性・充足可能性を検証。
- プログラミング：参照実装・AST変換・コンパイラ・単体テスト等。
- データ処理：生成した構造化データと参照プログラムから正解を計算。
- 長文：構造化された架空の事実から整合的な文章・質問を構成。
- 知識：ライセンスを確認した正確なデータを参照し、値の捏造をしない。
- ツール使用：仮想状態と決定的なツール実装を先に作り、達成状態で評価。

AIが必要ないカテゴリにはAI支援を持ち込まず、生成器の品質を独立したプログラム検証で確保する。

### 3.2 連続難易度

- **5段階固定の難易度を採用しない。** 操作上の入力は便宜上0.0〜100.0（連続値）などとする。
- カテゴリ/生成器ごとに、要素数、条件数、依存関係、要求する操作数、情報量、計算量などへマッピングする。
- `target_difficulty`（生成難易度）と `empirical_difficulty`（実測で校正した難易度）を分ける。
- 問題の条件数を増やすだけで難しくなると決めつけない。構造的な難しさ・制約の相互作用・解答に必要な操作を検証する。
- 実測校正が完了するまで「難易度50」が分野をまたいで同難易度であると断言しない。
- 正答率対難易度の曲線と、「正答率80%を維持できる推定難易度」などの補助指標を表示可能にする。問題数が少ないところの推定不確実性を隠さない。

### 3.3 多様性

単に値、人物名、変数名を変えただけの問題を大量に数えない。各生成器は少なくとも次を識別可能にする。

- **構造テンプレート**（解答に必要な操作の種類）
- 入力の表現（文章/表/JSON/コードなど）
- 難易度を決めた特徴量
- 回答形式（選択/短答/数値/構造化/コード）
- `seed`、生成器ID、生成器バージョン、出典/ライセンス（必要時）

構造的重複と表面的重複の両方を検出し、採択率・重複率を統計として記録する。

### 3.4 問題定義

問題には少なくとも次を含める（物理スキーマは実装側で決める）。

- `problem_id`、`schema_version`、`generator_id`、`generator_version`
- `category_id`、`subcategory_id`、複数の横断的能力タグ
- `seed`、`target_difficulty`、必要に応じた校正情報
- `prompt` と入力資料（必要なら問題ごとのファイル）
- `answer_spec`（正解、期待出力、テスト、許容誤差、採点方法等）
- `grading_type` と検証状態（verified/experimental等）
- `origin`（fixed/dynamic）、出典とライセンス（必要時）
- 正解参照情報への秘匿・アクセス制御。モデル入力に解答やテストの正解を混入させない。

問題IDは安定し、実行時は問題の実体と内容ハッシュを保存する。シードだけでは将来の生成コード変更による差異を吸収できない。

初期の分類体系は**16大カテゴリ**。各々に小カテゴリと独立した複数の生成器を追加できる。カテゴリを埋めるために品質の低い生成器を採用しない。

| 02 | 論理的推論 | 命題・真偽、含意、集合、順序、制約充足、反例、矛盾、演繹、関係追跡 |

各問題には主カテゴリのほかに横断タグ（日本語理解・多段階推論・長文・複数制約等）を付与する。集計時にはタグの重複を許すが、総合点へ**同一問題を重複加算しない**。

### カテゴリ管理UI（必須）

- **大カテゴリ → 小カテゴリ → 個別生成器** の三層選択。
- それぞれ一括ON/OFF、親カテゴリの一部選択（indeterminate）、検索、展開/折りたたみ、すべて選択/解除。
- 登録された生成器をレジストリから自動表示。生成器の追加に伴いUIコードへ手作業で項目を追記させない。
- 生成器の `verified / experimental / unavailable` 等の状態と、対応する難易度範囲を表示。
- 設定済み生成器数、カバー率、予想問題数を示す。
- 標準モードではverifiedのみを採用。未対応分野や不足する問題を**警告**し、勝手に別分野で代替しない。

### プリセット・モード（必須）

1. **総合・標準**：バージョン管理された分野・難易度・固定/動的比率に従う正式比較。
2. **幅広く評価**：最大限多くの小カテゴリをカバー。広さ重視。
3. **特定分野を深掘り**：選択した分野を高いサンプル数で評価。
4. **クイック**：少量の代表問題で簡易チェック。
5. **カスタム**：カテゴリ・生成器・配分・難易度・問題数・シードの詳細調整。

プリセット選択後も個別変更可能。ただし変更した時点で「プリセットから変更したカスタム」として表示し、正式な標準スコアと混同しない。ユーザー定義プリセットを保存・読み込み可能にする。

## 5. 固定問題＋自動生成問題を統合した標準評価

### 5.1 統合スコア

- 固定問題と動的生成問題を**同一ベンチマークで混合**し、正答率の総合値を示す。
- 初期案は固定50% / 動的50%。UIと設定ファイルで変更可能。
- 概要画面で総合正答率を示し、詳細画面で固定/動的それぞれの正答率・問題数・失敗例・難易度別曲線を確認可能とする。
- 速度、VRAM、RAM、電力などを単一の知能点へ強引に混ぜない。能力スコアとは独立して表示する。

### 5.2 公正な比較

- **標準ベンチマークの難易度分布は全モデルで共通**。連続難易度0〜100の全域を幅広くカバーし、実装初期は区間ごとの均等層化サンプリングなどを使用。
- 問題カテゴリ、回答形式、固定/動的混合比も同じ設定で揃える。生成器数の多いカテゴリを自動的に過大評価しない。
- まず問題セットを生成して**固定（freeze）**し、そのセットを複数モデルへ配布する。同一セッションでは動的問題も同一の実体を使用する。
- `benchmark_profile_version`、問題セットハッシュ、問題順序、`seed`、各分野の重み、採点器バージョン、利用した生成器バージョンを保存する。
- 固定問題が不足する分野・難易度では正式プロファイルを成立させず、問題数不足を明示。無断で固定/動的比率を崩さない。
- 暫定生成難易度と、モデル群のデータによる実測難易度を別に保存する。校正未完了の間は絶対的な公平性を宣言しない。
- 公開リポジトリの固定問題は学習データ汚染の可能性を伴う。スコアに出典・セット公開状況・作成日を記録し、プライベートなホールドアウトは**後からインポート可能**とする（公開リポジトリには含めない）。
- `Standard v1` のような正式バージョンは分野カバレッジと検証条件が満たされた場合のみ発行。開発途中は `Preview` や `Experimental` とする。

### 5.3 採点仕様

- 既定は明確に定義された正答/不正答。必要な問題だけ部分点を別に算出できる。
- 数値：厳密一致または問題ごとに定義された誤差。
- 選択式：正規化後の識別子を照合。選択肢の偏りを抑制。
- 文字列/構造化：仕様に基づく正規化、JSON Schema等の検証。
- コード：隔離環境内でテストを実行し、期待出力/テスト合格で判定。
- ツール使用：引数、呼出の成功、最終状態、達成結果等から判定。
- タイムアウト・エラー・無回答・採点不可を区別して保存。原則、割り当てた全問題を正答率の分母とし、未対応カテゴリは別扱いとして母集団を明示。
- 総合点の算定重みを記録し、固定/動的、分野、難易度の内訳と数学的に整合するようにする。

### 5.4 実行プリセットの規模（目標案）

| 種類 | 問題数の目安 | 用途 |
|---|---:|---|
| Smoke | 10〜20 | 実装・動作確認 |
| Quick | 100 | 簡易評価 |
| Standard | 約1,600 | 正式比較の将来目標（分野カバレッジが整ってから） |
| Full | 約8,000 | 詳細分析（高負荷） |
| Custom | 任意 | 特定分野、難易度、混合比の研究 |

問題数は調整可能。カテゴリが未整備の状態で1,600問の「完全な標準評価」を偽装しない。

## 6. 対応モデル・接続方式

### 6.1 基本要件

同じ評価エンジンから複数のモデルバックエンドを使える**アダプター構造**にする。各アダプターは、モデル一覧/登録、接続確認、機能検出、単発応答、必要なら会話継続、メトリクス収集、キャンセル、エラー通知を共通契約で実装。

| 接続方式 | 優先度 | 方針 |
|---|---|---|
| Hugging Face Transformers | 高 | WSL2上のローカルGPUで動かす。CPUモードも小規模検証可能にする |
| Ollama | 高 | ローカルサービスへの接続とモデル選択。利用可能な計測値を取得 |
| Codex CLI | 高 | 正式コマンド/イベントに基づく連携。ユーザー自身の認証済み環境を利用 |
| Codex App Server | 高 | 正式なプロトコル/認証方式に基づいて丁寧に実装。利用条件とバージョン互換を確認 |
| vLLM / llama.cpp | 中 | アダプター拡張ポイントを用意、必要に応じ実装 |
| OpenAI互換API等 | 低 | オプション。契約不要のMockサーバーで契約・データ型をテスト |
| Claude / Claude Code | 保留 | ユーザーは契約なし。初期実装・実接続試験の必須条件にしない |

**GPT等へのアクセスを保証してはならない。** 利用可否はユーザーのプラン、機能権限、公式対応状況、利用枠、利用規約に依存する。

### 6.2 Codex CLI / App Serverの留意点

- 公式のサポートされた利用方法のみを使用し、非公式のトークン抽出、保存済み認証情報の解析・転用、制限回避、UI自動操作での疑似API化をしない。
- Codex CLI連携は明示的に有効化できるようにし、サブプロセスの引数・JSONイベント・終了コード・タイムアウトを安全に処理する。`shell=True` 等の危険な実装を避ける。
- Codex App Serverは公式のプロトコルに沿って接続し、初期化、スレッド管理、終了イベント、キャンセル、エラー、認証失効・更新を扱う。
- **OpenAI公式のオープンソース向けSign in with ChatGPT** が利用条件を満たす場合に、公式フローで接続する。モデル一覧は利用権限の確約ではないため、利用権限は実際のリクエスト成功等で判定する。
- 公開リポジトリであっても、アプリが公式プレビュー条件や認証要件を満たすかを文書化し、未承認・未利用環境では接続不可として扱う。
- ユーザーのログイン済みCodex CLI環境から起動する場合でも、CLIがホストファイルや開発ツールにアクセスし得る。**通常のテキストQ&Aで不要なツールを与えず、最小権限で隔離し、必要な制御が保証できない経路は正式評価から除外する。**
- これらのエージェント経由の回答は、モデル単体の生テキスト推論とシステムプロンプト/ツール/エージェント動作が異なるため、結果に `codex-agent` 等の評価経路を明記し、単純な生モデル評価と混同しない。
- サブスクリプション利用枠に配慮し、実行前に推定リクエスト数・中止操作・レート制限処理を提供する。自動で課金APIへ切り替えない。
- 実アカウントでの検証が不可能なら、**アダプターの実装とMockプロトコル試験まで行い、実接続は `NOT_VERIFIED` と明示**する。

### 6.3 登録情報

モデルID、リビジョン/版、モデルファイルのハッシュ（可能なら）、量子化方式、バックエンド、チャットテンプレート、コンテキスト長、モデルの対応機能、推論パラメーター（temperature、seed、max tokens、reasoning effort対応時等）を記録する。

**モデルの能力とアダプターの機能は別**。テキスト専用、ネイティブツール、画像入力などに対して機能検出を設け、未対応を不正解として処理しない。

## 7. ツール使用・エージェント評価

ツール評価は単純なテキスト応答と混同しない。次の独立モードを用意する。

1. **テキスト型**：ツール仕様を問題文に提示し、使うべきツール名と引数をJSON等のテキストで回答。通常のテキストLLMでも評価可能。ただし実際にツールを呼び出しているわけではない。
2. **ネイティブFunction Calling型**：対応バックエンドで構造化ツール呼出を受け取り、ツール名/引数/スキーマ遵守を判定。実装時はモデル・バックエンドのサポート範囲を確認。
3. **複数ターンエージェント型**：模擬ツールを実行→結果をモデルへ返却→続く呼出/最終回答を受け取る。最終状態・許可されない変更・効率・成功率を判定。

模擬環境は、電卓、架空のDB、架空のファイル、スケジュール、タスク、検索、模擬HTTP API等から段階的に導入。外部APIやユーザーの実データを必要としない。**問題ごとに環境をリセット**する。

採点内訳：ツール選択、引数、スキーマ、実行成功、最終状態、最終回答、不要な操作、禁止操作。各モード別にスコアを記録し、モード間の点数を根拠なく同一視しない。ネイティブツールをサポートしないモデルへ無理に強制しない。

## 8. 正確性・速度・リソースの計測

### 8.1 能力指標

- 統合正答率および分野別正答率。
- 固定問題・動的生成問題の正答率、問題数、難易度分布。
- 難易度曲線、失敗傾向、問題形式別/能力タグ別成績。
- 指示遵守率、正常完了率、タイムアウト/採点不可率。
- ツール使用等の追加能力は対応モードごとに区別。

### 8.2 時間指標

- 全体実行時間と1問ごとのレイテンシ、中央値（P50）、P95。
- 出力トークン生成速度（decode tok/s）：バックエンドが信頼できるトークン数/時間を提供する場合のみ。
- TTFT（ストリーミングで最初のトークン時刻が観測できる場合のみ）。
- Prefill速度、スループット、モデルロード時間：実測可能な場合のみ。
- 性能比較には問題回答時の実行値と**統一した入力/出力長による専用速度測定**の両方を設計する。
- Codex等のエージェント接続は通信・内部処理を含むE2E時間として区別。純粋なモデルのtok/sと偽って表示しない。

### 8.3 リソース指標

- GPU名、CPU、RAM、CUDA、ドライバー、バックエンドのバージョンを記録。
- Peak VRAM、RAM、GPU使用率、消費電力（対応時）など。
- GPU全体のメモリとプロセス単位の割当を混同しない。
- 利用できない値は0とせず `N/A`、測定不可理由を付ける。
- 量子化違い・ハードウェア違いの実行構成を個別に保存する。

### 8.4 公平性

- 同一問題セット、モデル別の明示された推論設定、共通の実行ポリシー。
- 単独モデルの順次実行を既定とし、GPU干渉を避ける。並列実行は将来任意でサポートし、測定モードを明記。
- キャッシュ/ウォームアップ/プロンプト長/出力長/バッチサイズ/ストリーミング/推論努力レベルを記録。
- 「モデルの回答能力」「モデル推論速度」「エージェント経由の応答性能」は別の指標として扱う。

## 9. 実行制御と状態保存

### 実行前

- モデルを複数登録・選択できる。モデル登録時に接続確認・対応機能・モデル版を示す。
- プリセット、カテゴリ選択、問題数、連続難易度の範囲と分布、固定/動的比率、シード、評価オプションを指定。
- 実行前に**問題セットを確定**し、内容ハッシュと問題数の内訳を表示。
- 推定所要時間（根拠ある場合のみ）、推定リソース、未対応機能、隔離環境の状態を確認できる。
- 未検証のモデル接続や隔離不足は警告し、危険な実行はブロックする。

### 実行中

- 進捗：合計/処理済/正解/不正解/タイムアウト/実行エラーの件数とパーセンテージ。
- **暫定の総合正答率、固定/動的それぞれの正答率、分野別の簡易成績**。
- 時間：経過時間、直近/平均レイテンシ、計測可能な速度、推定残り時間（安定してから）。
- UIへイベントを逐次配信（SSEやWebSocketなど）。長時間で切断されても再接続できる。
- キャンセル/一時停止/再開。回答完了ごとに進捗保存。異常終了した問題だけ再試行可能。
- 進捗段階の偏りに注意する。固定シードによるシャッフル等で初期の暫定スコアが特定難易度に偏ることを減らし、**暫定値であると表示**する。
- 最終レポートと混同しない。途中の部分集計は随時更新、最終スコアは実行終了後に確定。

### 実行後

- 実行履歴の一覧、詳細、再比較、CSV/JSON/Markdownでのエクスポート。
- 再開可能な未完了ランと、確定済みのランを区別。
- 問題、回答全文、採点理由、対応するテスト/ツール履歴、時間と環境情報を追跡できる。
- 大きな回答ログや問題セットはSQLite外のartifactに分離してよいが、参照整合性とバックアップ方法を文書化する。

8. **Generators / Coverage**：16大カテゴリと小カテゴリ、個別生成器、品質ステータス、実装カバレッジ。

## 11. 隔離とセキュリティ — 必須要件

このシステムはLLMが生成したコード、シェル命令、ツール呼出を扱う可能性があるため、隔離は飾りではなく**必須の実装・検証対象**とする。

### 11.1 通常のコード実行

- コード実行は**ホスト上で直接行わない**。Docker等の隔離実行環境（可能ならrootless、専用ワーカー）を用いる。Dockerが利用できない場合、コード実行採点は無効。
- 実行ごとに使い捨て環境を作成。ホストホーム、`.ssh`、トークン、ブラウザ認証情報、Git設定、Dockerソケットをマウントしない。
- デフォルトでネットワーク禁止、root権限禁止、`no-new-privileges`、capabilities削除、読み取り専用ルートFS、制限付き作業用ディレクトリ、CPU/RAM/PID/ファイルサイズ/実行時間の制限。
- コンテナは完全なセキュリティ境界と断定しない。対応するOS隔離機構やホスト側の最小権限も検討する。
- タイムアウト、OOM、クラッシュ、隔離違反を検知して記録する。失敗時の後片付けを保証する。

### 11.2 模擬ツール / Codexアダプター

- ツール使用ベンチマークは模擬世界（仮想DB/仮想ファイル等）で行い、本物のOS操作を既定としない。
- 「正解データ/採点器」へのアクセスをモデル側へ許可しない。
- Codex CLI/App Server等のエージェントがホストコマンドを使える場合、**最小権限・ツール制限・サンドボックス機能の確認**を優先する。安全な制限が不可能な場合は正式な評価経路に採用しない。
- 本物の認証トークンを生成コード、サブエージェント、隔離ワーカーへ渡さない。認証管理プロセスを分ける。

### 11.3 ローカルWeb / Public GitHub

- サービスは既定で `127.0.0.1` にバインド。外部公開しない。CORSとローカルWebからの不正リクエスト、CSRF/Originの検証等に注意。
- パス操作、任意ファイル読み込み、ZIP展開、アップロード、SQL、shell引数、外部URL、プラグイン等を検証し、パストラバーサル/コマンドインジェクション/SSRF等を防止。
- 認証情報は保護されたローカルストレージ/公式方式へ。ブラウザのlocalStorage、Git、ログ、JSONエクスポートへ秘密情報を残さない。
- `.gitignore` / `.env.example` / Secret scan / CIを整備。Publicリポジトリ前提なので、テスト用ダミー以外のシークレットを含めない。
- 固定問題の外部データセットについて、ライセンス/再配布条件を遵守。ライセンス未決定の外部資料を公開リポジトリへコピーしない。

### 11.4 セキュリティの受け入れテスト

- 禁止ファイルの読み取り失敗、ネットワーク接続不可、ファイル書き込み領域制限、時間制限、CPU/RAM制限、無権限実行、ジョブ削除/掃除が**実際に確認できる**こと。
- 隔離できない状況では実行が安全側に停止（fail-closed）し、その理由がUIに表示されること。
- 認証情報がログ・エラー表示・コミット・結果ファイルに現れないことを検査する。

## 12. 開発中の実回答テスト（ユーザーが指定した特別ルール）

**開発中にAIが問題を解くテストは、通常の正式ベンチマーク経路とは分け、Codex Cloudのサブエージェントが実際に問題を解く方式だけにする。**

### 手順

1. 生成器がカテゴリ・難易度・シードを変えて検証済みの少数問題を作る。
2. **問題本文だけ**を開発用回答サブエージェントへ渡す。正解、生成規則の秘匿部分、採点器の参照実装は渡さない。可能なら読み取り可能な作業空間からも分離する。
3. サブエージェントが回答したら、通常の採点器で採点する。誤答はAIの失敗、設問の曖昧さ、正解の不具合、採点器の不具合に分けて調査する。
4. 生成器・難易度・採点器へのフィードバックレポートを `dev_reports/` 等に残す（本番の `results/` とは別）。
5. **サブエージェントの結果を、正式なGPT/Codexの性能値、モデルランキング、公開比較スコアに含めない。** 診断上の参考値としてのみ使用。
6. サブエージェント機能が利用できない場合、この試験を `SKIPPED` と記録する。実施していないテストを成功と報告しない。

### 別途必須のソフトウェアテスト

上記は問題の妥当性検証の補助であり、テスト代替ではない。以下は非AIの自動テストとして必ず実施する。

- 生成問題の解答・正解・検証の整合性と一意性（必要な場合）
- seed/バージョン/問題セットハッシュによる再現性
- 連続難易度パラメーターの単調性/統計的な変化（可能な範囲）
- 重複除去、カテゴリ自動登録、プリセット選択、スコア集計
- 正答率の分母、タイムアウト、欠損値、未対応機能の扱い
- 一時停止/再開/再試行/異常終了の復元
- UI、API、CLIの統合、DBマイグレーション
- Codex CLI/App Serverのモック化したイベント通信・失敗処理・タイムアウト・認証なし状態
- 隔離実行の安全性

**Codex Cloudで実際のサブスクリプションモデルを大量に呼び出して正答率を測る必要はない。** 正式なモデル接続の実測はユーザーのローカル実行環境が利用可能なときの検証項目とする。

## 13. データ永続化と成果物管理

- SQLiteにモデル登録、問題メタデータ、セット定義、ラン、進捗、採点、主要メトリクス等を保存。
- 問題セットの実体・生成器版・正解データ・実行時プロファイルを版管理。`seed`だけでは再現性が不十分なため問題本文・期待値を確定保存する。
- JSONL / CSV / Markdownレポートにエクスポート可能。巨大な問題群・回答ログは圧縮や分割を検討。
- Public GitHubでは生成器・テスト・少量のサンプル・検証済み公開問題を管理。大量成果物は必要ならReleasesや外部保存を**任意で**使うが、ユーザーの承認なしに外部アップロードしない。
- データの入出力を明確に分け、既存ユーザーデータを上書きしない。シークレット/個人情報を除外。
- オープンソースのコードライセンスは**ユーザー未確定**。MITなどを提案してよいが無断で確定しない。外部問題データのライセンスは個別に扱う。

## 14. 段階的な開発計画と完了基準

**各フェーズはコード、テスト、起動手順、実行結果が揃って初めて完了。** 不可能な項目は代替を示して未完了として残す。Codex Cloudの1タスクで全機能が終わるとは限らないので、`docs/ROADMAP.md` と `docs/STATUS.md` を更新し、後続タスクで再開できる状態にする。

### Phase 0 — 調査・セットアップ

- リポジトリの既存状態を調査。依存関係と開発環境を決める。
- Pythonバックエンド、Web、CLI、DB、テスト、CIの最小構成。
- アーキテクチャ/前提/公式ドキュメントに関するADRとREADMEを整える。
- **合格条件**：Codex CloudのCPU環境で依存解決・lint・型チェック・テストが動く。秘密情報もGPUも不要。

### Phase 1 — 縦方向の動く最小構成

- 問題スキーマ、生成器レジストリ、シード再現、検証、採点、固定/動的混合、SQLite保存、CLI。
- まず数学・論理・データ処理・コードの一部を実装し、少なくとも複数の異なる問題構造を作る。
- Fake/Mockモデル経由で1回のランを完了し、総合/固定/動的の正答率と問題別結果を取得。
- **合格条件**：同じseedで同じ問題を取得、採点が期待どおり、テストが通る。雛形ではなく実働する。

### Phase 2 — ベンチマーク設定とWeb UI

- 黒基調UI、モデル/生成器一覧、カテゴリツリー、プリセット、難易度、問題数、固定/動的比率。
- ラン開始、進捗イベント、暫定結果、結果概要、詳細ラン、実行履歴、比較画面の初版。
- **合格条件**：ブラウザで設定→実行→経過観察→結果閲覧が一通り可能。カテゴリ全体/個別選択が働く。

### Phase 3 — 実モデルアダプターと計測

- Transformers、Ollamaのローカルモデル接続。CPU/Mock環境でもテスト可能。
- 正確性/速度/メモリ/実行条件収集、欠損値の正しい表現。
- Codex CLI / App Serverの**公式仕様を確認した丁寧な実装**。課金APIがなくてもMockテスト。未認証時に安全に失敗。
- **合格条件**：ローカルでモデル試験可能な手順と自動テスト。Codexは実接続を未検証ならその旨明記。

### Phase 4 — 長時間実行と隔離

- 一時停止/再開、途中復元、タイムアウト/エラー処理、モデル順次評価、問題セット共有。
- 隔離コード実行、模擬ツール基盤、悪意あるコードを想定した安全テスト。
- **合格条件**：ランの中断後に再開でき、回答や採点が二重計上されない。隔離不能時は安全側に停止。

### Phase 5 — 問題生成器の拡充とツール評価

- 16大カテゴリの管理体系を実装し、検証済み生成器を段階的に増やす。初期の品質目標は20〜30種類、その後50〜80種類、長期的には100種類以上を目標とする（**数合わせをしない**）。
- テキストツール選択、ネイティブツール利用、複数ターンの模擬エージェント評価を、対応可能な範囲で独立モードとして実装。
- サブエージェントによる開発用問題解答試験を行い、レビューと採点不具合の改善を実施。
- **合格条件**：新規生成器が自動登録され、カテゴリ検索・採点・再現性試験を通る。各種ツール評価は対応/未対応を誤表示しない。

### Phase 6 — 研究用としての品質仕上げ

- 難易度の実測校正に備えた結果収集・分析、出題バランス、重複/汚染リスクの資料化。
- P50/P95、分野別・難易度別の詳細分析、エクスポート、性能比較の注意書き。
- 実験環境の再現手順、WSL2セットアップ、FAQ、制限事項、セキュリティドキュメントを整える。
- **合格条件**：READMEの手順で起動でき、統合テストとセキュリティテストが通り、既知の未検証機能と対象外範囲を一覧できる。

### Codexの自律的な進め方

- それぞれのフェーズ終了時に、完成・未完成・テスト結果・PR/コミット・今後の課題を`docs/STATUS.md`へ記録する。
- 作業継続が可能なら次フェーズへ進む。重大なブロッカー以外でユーザーへ細かな確認を連発しない。
- 公開リポジトリのメインブランチへ無確認で危険な破壊的変更を行わない。ユーザーの既存リポジトリ運用ルールを優先。

## 15. 検証観点（受け入れテスト例）

1. **再現性**：同じ生成器バージョン・seed・設定で同じ問題セットハッシュになる。
2. **問題品質**：論理パズルの一意解、数学の参照計算、コードの隔離テストが通る。
3. **分布**：標準プロファイルに定義されたカテゴリ・難易度区間・固定/動的比率を満たす。満たせなければ正式評価不可。
4. **モデル公平性**：2モデル比較時、問題セットのID/内容/採点規則が一致する。
5. **スコア整合**：固定/動的・各カテゴリの集計から総合スコアが再計算できる。欠損・タイムアウトの分母が正しい。
6. **連続難易度**：0〜100の値を設定・保存し、パラメーターへの変換と難易度帯別分析が可能。
7. **カテゴリUI**：大→小→生成器の一括/個別ON/OFF、部分選択、検索、プリセットの変更が反映される。
8. **進捗**：実行中に処理数・暫定正答率・固定/動的内訳が更新され、接続再開で状態が戻る。
9. **中断・再開**：意図的停止/異常終了から安全に再開でき、問題が二重計上されない。
10. **速度・リソース**：実測できる指標を保存し、取得できない値をN/Aにする。実行条件差をUIで警告。
11. **Codex接続**：Mockの成功・認証欠如・通信失敗・中断・利用枠エラーを正しく扱う。実アカウントがなければ未検証。
12. **ツール評価**：テキスト型・ネイティブ型・エージェント型を区別し、仮想世界の許可外変更を検知する。
13. **隔離**：ホストの秘密情報にアクセス不可、外部ネット不可、資源制限が働き、隔離不能なら実行不可。
14. **開発サブエージェント**：問題のみ渡して実解答を取得し、採点器と比較。結果が正式スコアに混入しない。
15. **Public適性**：ライセンス違反データ、トークン、認証キャッシュ、ローカルモデル重みをコミットしていない。
16. **セットアップ**：新規環境からのCPU開発起動と、WSL2/GPU環境のユーザー向け起動手順がある。

## 18. 今すぐ開始すること（Codexへの最終依頼）

上記方針に基づき、ユーザーが指定したリポジトリで開発を開始してください。

1. リポジトリを調査して開発ロードマップを具体化する。
2. **Phase 0 → Phase 1**の順に、実働する最小構成を最優先で完成させる。時間・作業可能範囲が許せば後続フェーズも自律的に進める。
3. 変更とテスト結果を記録し、問題があれば修正する。
4. UIは黒背景で洗練された研究ダッシュボードにする。
5. Codex CLI / App Serverは公式接続を丁寧に実装するが、開発中の**実回答試験はサブエージェントのみ**とし、正式なモデル接続実測は不要。
6. 隔離と課金/認証の安全性を犠牲にして機能を実装しない。
7. プロジェクトの目的を損なわず、将来の生成器追加・モデル追加・測定指標追加がしやすい構成にする。
8. 完了時には、実装した機能、未実装項目、実際に通ったテスト、ローカル起動方法、次のフェーズを日本語で簡潔に報告する。

**最重要：見た目や生成器数の多さより、検証可能性・再現性・安全性・実際の動作を優先する。**
